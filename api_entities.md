# Модель данных и расчёт выплат курьерам

Автор: Ильнур Аскаров. Когорта: 49. API nickname: `ilnur_askarov`.

## Поля витрины

Детализация `cdm.dm_courier_ledger`: один курьер за один календарный месяц.

| Поле | Источник / правило |
|---|---|
| id | Суррогатный ключ витрины |
| courier_id | Внешний ID из `/couriers._id`; `dds.project5_couriers.courier_key` |
| courier_name | `/couriers.name` |
| settlement_year, settlement_month | Год и месяц даты заказа в `dds.dm_timestamps`, связанной с `dds.dm_orders.timestamp_id` |
| orders_count | Число связанных доставленных заказов месяца; одна доставка на заказ |
| orders_total_sum | Сумма полных стоимостей заказов из MongoDB |
| rate_avg | Средняя оценка доставок курьера за месяц, каждый заказ имеет одинаковый вес |
| order_processing_fee | `orders_total_sum * 0.25` |
| courier_order_sum | Сумма вознаграждений за отдельные заказы; ставка определяется средним рейтингом месяца |
| courier_tips_sum | Сумма `tip_sum`, каждый заказ учитывается один раз |
| courier_reward_sum | `courier_order_sum + courier_tips_sum * 0.95` |

Ставки: `<4` → 5%, минимум 100; `[4,4.5)` → 7%, минимум 150;
`[4.5,4.9)` → 8%, минимум 175; `>=4.9` → 10%, минимум 200 рублей за заказ.
Ставка выбирается по неокруглённому среднему рейтингу. Расчёты ведутся в NUMERIC/Decimal.
Денежные итоги округляются до копеек после суммирования.

## DDS: существующие и новые таблицы

| Таблица | Статус | Использование |
|---|---|---|
| dds.dm_orders | Существующая, расширяется | `id`, `order_key`, `timestamp_id`; добавляется nullable FK `project5_courier_id` |
| dds.dm_timestamps | Существующая | Дата заказа, год, месяц; дата доставки не определяет месяц выплаты |
| dds.dm_users, dds.dm_restaurants, dds.dm_products, dds.fct_product_sales | Существующие | Продолжают наполняться исходными DAG; проект их не заменяет |
| dds.project5_couriers | Новая | Курьер: суррогатный ключ, внешний ID, имя |
| dds.project5_deliveries | Новая | Доставка, ссылки на заказ и курьера, время доставки, оценка, чаевые |
| dds.project5_order_amounts | Новая | Полная стоимость одного заказа, PK/FK на `dds.dm_orders.id` |

Связи образуют снежинку: доставка → курьер; доставка → заказ → дата/покупатель/ресторан;
стоимость заказа → заказ. Дополнительная ссылка заказ → курьер добавлена миграцией.
Исходные таблицы не удаляются. Названия новых DDS/STG-таблиц имеют префикс `project5`,
чтобы не конфликтовать с учебными таблицами.

Полная стоимость берётся из поля `cost` Mongo-документа
`stg.ordersystem_orders.object_value`. Для старого формата без `cost` используется
`SUM(price * quantity)` по всем `order_items`. Сумма API доставки не используется.
Равные по цене позиции не удаляются. Поле `sum` API доставки не участвует в расчётах.

## Сущности API и STG

| Метод | Поля | Использование |
|---|---|---|
| /couriers | `_id`, `name` | Ключ и имя курьера |
| /deliveries | `delivery_id`, `order_id`, `courier_id` | Ключ доставки и связи |
| /deliveries | `delivery_ts` | Окно выгрузки `[from,to)` |
| /deliveries | `rate`, `tip_sum` | Оценка и чаевые |
| /deliveries | `order_ts` | Контроль полноты для ещё не связанных заказов; для витрины используется дата подсистемы заказов |
| /deliveries | `address`, `sum` | Сохраняются в исходном JSON; в расчётах не используются |

`/restaurants` не требуется: рестораны уже приходят из подсистемы заказов.

`stg.project5_couriers`: `object_id`, полный исходный `object_value JSONB`, `loaded_at`.
`stg.project5_deliveries`: `object_id`, полный исходный `object_value JSONB`, `delivery_ts`, `loaded_at`.
JSON сохраняет все поля, включая неизвестные загрузчику; JSONB не сохраняет пробелы и порядок ключей.
`stg.project5_loads` фиксирует успешно загруженные окна и число объектов.

Для курьеров сортировка `id ASC`, для доставок `_id ASC`. Все страницы читаются
с `limit=50`, `offset=0,50,...` до неполной или пустой страницы. По умолчанию
загружаются семь суток перед `data_interval_end` родительского DAG.
Полное окно заменяется в одной транзакции: ошибка API откатывает всю замену.
История за пределами окна сохраняется. Переезд даты доставки внутри нового ответа
обрабатывается UPSERT по `delivery_id`.

## Оркестрация и обновления

Существующий DAG заказов сохраняет свои задачи и расписание. В него добавляются
запуск STG DAG → ожидание → запуск DAG измерений → ожидание.
Загрузка новых фактов зависит одновременно от завершения исходных задач и измерений.
Затем пересчитывается CDM. Сенсоры работают в `reschedule`, не удерживая worker.
Дочерние DAG запускаются родительским ежедневно (или чаще); отдельное расписание
им не назначается, чтобы они не создавали независимые конкурирующие циклы.

DDS обрабатывает все сохранённые доставки заново: отсутствующие заказы не теряются
из-за продвижения ID-курсора, а изменения старых сумм и оценок учитываются.
Перед выплатой проверяются ссылки. Несколько разных доставок одного заказа
вызывают ошибку вместо двойной выплаты; такой случай требует уточнения бизнес-правила.

CDM содержит только закрытые месяцы, для которых окна API покрывают полный месяц.
За предыдущий месяц полнота обязательна; при её отсутствии расчёт останавливается.
Исторические полные месяцы также пересчитываются, включая их новый средний рейтинг.
UPSERT сохраняет ID существующих строк, удаление убирает исчезнувшие группы.
Поздние доставки учитываются в месяце заказа. Исправления старше семидневного окна
загружаются явным повторным запуском с `from`/`to`.

API не предоставляет snapshot token: повтор ключа между страницами обнаруживается
и останавливает выгрузку. Полностью исключить изменения источника во время paging
без поддержки snapshot со стороны API нельзя; повторная загрузка перекрывающегося
окна уменьшает этот риск.

Все даты источника считаются бизнес-временем без часового смещения, как в спецификации.
Месячная граница и `data_interval_end` интерпретируются в той же зоне; UTC — настройка
учебного окружения по умолчанию. При смене бизнес-зоны нужно согласовать расписание
родительского DAG и преобразование его интервала.

## Исходная загрузка для пустого тренажёра

`project5_orders` включает создание таблиц, загрузку MongoDB (`orders`, `users`,
`restaurants`), PostgreSQL (`outbox`, `ranks`, `users`), измерения и товарные факты.
В существующем хранилище вместо этого DAG подключается расширение
`extend_orders_dag` к действующему DAG; параллельная запись двух базовых загрузчиков
в одни таблицы не допускается.

В новом DWH создаются `dds.dm_users`, `dds.dm_restaurants`, `dds.dm_products`,
`dds.dm_orders`, `dds.dm_timestamps`, `dds.fct_product_sales`.
Детализация товарных фактов — строка заказа (`order_id`, `line_no`),
повторяющиеся позиции сохраняются. Товарные факты учитывают CLOSED-заказы.
Для курьерской витрины используется фактическое наличие доставки и полная цена
Mongo-заказа, а не количество товарных строк.

MongoDB обновляется по `update_ts` с перекрытием семь суток; одинаковые timestamp
не пропускаются благодаря полному чтению курсора и повторному включению границы.
Все пачки коллекции и checkpoint фиксируются в одной транзакции.
Mongo-документы сохраняются в JSONB с ISO-датами и строковыми ObjectId.
Удаление Mongo-документа из источника этим инкрементом не обнаруживается;
для удаления нужен отдельный snapshot/change-stream механизм.

Бонусные источники сохраняются в `stg.project5_bonus_ranks`,
`stg.project5_bonus_users`, `stg.project5_bonus_events`,
затем в одноимённые DDS-таблицы. `outbox.event_value` преобразуется из JSON-текста
в JSONB. Ранги и пользователи перечитываются полностью; outbox читается по ID
с перекрытием последних 10000 ID. Исправления более старых outbox-записей
требуют сброса checkpoint `bonus_events` в `stg.project5_state` и перезагрузки.
Бонусные суммы не используются вместо полной стоимости заказа при выплатах курьеру.

## Фактическая фильтрация учебного API

При проверке 8 ноября 2026 года API вернул для `to=2026-11-08 02:00:00`
заказы с доставкой после 02:00. Это указывает на фильтрацию по `order_ts`,
в отличие от описанного в спецификации `delivery_ts`.
Чтобы не потерять доставку старого заказа в начале окна, запрос читает
историю с 1970-01-01 до правой границы, а клиент отбирает только
`from <= delivery_ts < to`. Подтверждается инвариант `order_ts <= delivery_ts`.
Это корректно при обеих трактовках серверного фильтра, но требует чтения
большего числа страниц. В STG сохраняются только доставки нужного окна.
Пагинация использует длину исходной страницы, даже если ни одна её запись
не вошла в окно. Пустая после фильтрации страница не завершает выгрузку.
